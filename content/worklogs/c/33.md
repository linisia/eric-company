**Q1. 자연어 → Figma/Notion 자동 갱신 사이클 — 자율 vs HITL 분기점**

부원 헤드리스에서 이미 MCP `mcp__notion__notion-update-page` · `mcp__figma__use_figma` 가 닿음. 자율 가능 구간을 코드 결로 나누면:

- ✅ **자율 OK (rw 안전)**: ① Notion 카드 frontmatter 갱신(figma_node_id·screen_id·priority 같은 결정론 필드), ② sitemap.md `(부원 추정)` 라벨 박힌 후보 행 append, ③ 변경 이력 1줄 자동 append(`YYYY-MM-DD HH:MM · 부원 · {변경요약}`), ④ Notion 페이지 ↔ Figma node link 양방향 연결 검증·복구.
- ⚠️ **HITL 필수**: ① Figma 컴포넌트 신규 생성·삭제(디자인 결재 영역), ② Notion 페이지 신규 생성(스키마·계층 영향), ③ 화면 ID 재명명(Firebase 통계 누적 키 깨짐 — Eric 절대원칙), ④ 양식 v2 → v3 마이그레이션 같은 일괄 스키마 변경.
- 🚨 **금지(절대원칙 그대로)**: Figma·Notion 임의 삭제·구조 재배치.

**분기 룰 한 줄**: "결정론 + 되돌릴 수 있음 + ID 키 안 깸" 셋 모두면 자율, 하나라도 깨지면 HITL. 코드로는 `op.idempotent && op.reversible && !op.touches_screen_id` 게이트.

**Q2. 양식 v3 (3섹션) 충분한가?**

3섹션(한 줄 요약 / 사용 컴포넌트 / 변경 이력) + frontmatter면 **자동 갱신 사이클 닫힘**. 추가 권장 필드 1개만:

- frontmatter에 **`auto_sync: {last_run, source, drift}`** — 마지막 자동 동기화 시각·소스(notion|figma|both)·드리프트 감지 결과. 이게 박혀야 누적 데이터 → 분석 단계에서 "동기화 신뢰도" 메트릭이 잡힘. 없으면 변경 이력만 봐선 자동/수동 구분 못 함.

본문 3섹션은 단순화 잘 됨 — 양식 v2 8섹션은 LLM 분석 입력으로 노이즈 컸음(§3 매핑 룰 떨군 협의 단계 페이지가 그 증거).

**Q3. `scripts/screen-sync.sh` 필요한가?**

필요. 단 셸 한 줄짜리 X — **3단 파이프**:

```
screen-sync.sh {screen_id}
  ├ fetch    : notion-fetch + figma get_metadata → JSON cache (.cache/screens/{id}.json, TTL 24h)
  ├ diff     : cache vs 현 카드 frontmatter → drift 표(필드별)
  └ apply    : drift 중 자율 OK 필드만 카드 갱신 + 변경 이력 append (HITL 필드는 결재 큐로)
```

핵심은 **캐시 TTL**. Notion/Figma fetch 비용·rate limit 무거움. cache 안 박으면 부원 호출마다 매번 fetch — 한도 빨리 닳음. `.cache/screens/{id}.json` 24h TTL이면 같은 사이클 안에서 화면 N개 처리해도 fetch 1회로 끝.

스크립트화 임계: 3+ 부원이 같은 fetch 결 반복하기 시작하면 스킬화 후보(SOUL 룰 #3).

**Q4. 변경 이력 누적 → LLM 분석 입력 형식**

LLM이 통찰 잘 뽑는 형식 = **JSONL + 화면 ID partition**:

```jsonl
{"ts":"2026-05-18T16:30Z","screen_id":"LV_01","actor":"c","op":"update","field":"components","before":[...],"after":[...],"source":"figma"}
{"ts":"2026-05-18T16:31Z","screen_id":"LV_01","actor":"eric","op":"approve","field":"priority","before":"medium","after":"core","source":"manual"}
```

이유 — ① 화면별 시계열 분리(`grep '"screen_id":"LV_01"'` 한 줄로 한 화면 전체 이력), ② before/after 페어로 LLM이 "왜 바뀜?" 추론 가능, ③ actor+source 분리로 자동/수동/Eric 결재 결 구분(이게 Q1의 자율 vs HITL 검증 입력으로 되먹임).

마크다운 변경 이력은 사람이 읽음, JSONL은 LLM이 읽음. **둘 다 박는 게 정답** — 카드 본문 §3 변경 이력은 사람용 한 줄, 같은 이벤트가 `analytics/changes.jsonl`에 1행 동시 박힘. 카드 작성 자동화 스크립트가 이중 기록.

### 배운 점 (← dream 입력)
- **패턴/원칙 (자율 vs HITL 분기 룰)**: 자동화 사이클 설계 시 `idempotent && reversible && !touches_id_key` 세 게이트 모두 통과해야 자율. 하나만 깨져도 HITL. ID 키(화면 ID·Firebase 키)는 누적 통계 깨짐 → 어떤 경우에도 자율 금지.
- **새로 통한 것**: 변경 이력은 **마크다운(사람) + JSONL(LLM)** 이중 기록이 정답. 한 쪽만 박으면 분석 입력 or 가독성 둘 중 하나가 죽음. JSONL은 화면 ID partition이 핵심 — grep 한 줄로 시계열 뽑힘.
- **사이클 설계 메타**: fetch 무거우면 **캐시 TTL**이 한도 보호의 1차 방어선. 부원 N명이 같은 fetch 반복하기 전에 캐시 박는 결로 잡아야 함.
