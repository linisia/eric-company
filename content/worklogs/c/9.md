## #9 🛠️ #T-C-102 step1 — staticrypt 설치 + fixture 매니페스트

- 일자: 2026-05-14
- 작업자: 최대리
- 지시: 김부장

> "Phase 4 staticrypt 통합. 빌드 후처리로 `공개: password` 페이지만 AES 암호화."

### 시작
큐 첫 미처리 H3 = `#T-C-102`. step3·4 종결 확인(#7·#8). 작업량 큼(설치·후처리·매니페스트·secret·검증) → step 분할. **step1은 설치 + fixture + manifest까지**.

### 실행
1. `npm install --save-dev staticrypt` (v3.5.4). `npx staticrypt --version` 확인 ✅.
2. 설계 갈림길 정리: 워크로그(`worklogs/c.md`)는 한 페이지에 섹션별 password 섞임 → sync-content가 placeholder로 마스킹(현 동작 유지). **staticrypt는 frontmatter `공개: password` 페이지 통째 암호화**로 분리. manifest로 두 메커니즘 연결.
3. `scripts/sync-content.mjs` 패치 — `seedFixtures()` 추가. `content/fixtures/public.md` + `content/fixtures/password.md` 생성(frontmatter `공개: …` 박힘). private은 sync 단계에서 제외(빌드 자체 미포함).
4. manifest 출력 — `encrypted-paths.json` (quartz root)에 password 페이지 경로 목록 + 생성 시각. encrypt-pages가 다음 사이클에 소비.
5. 통합 빌드: `node scripts/sync-content.mjs && npx quartz build` → **12 input → Emitted 99 files in 695ms** ✅. `public/fixtures/{public,password}.html` 2편 생성, private 부재 확인.

### 결과
- staticrypt v3.5.4 dev-dep 추가 ✅
- `scripts/sync-content.mjs` — `seedFixtures()` + manifest 출력 로직 패치 ✅
- `content/fixtures/{public,password}.md` 2편 — 페이지 단위 frontmatter `공개:` 분기 시드
- `encrypted-paths.json` — password 페이지 경로 1건(`fixtures/password.html`)
- private fixture는 sync 제외로 빌드 미진입(분기 회로 정상)
- 큐 헤더 ✅ **마킹 안 함** — encrypt-pages 미작성, secret 미통합. step2에서 종결.

### 배운 점 (← dream 입력)
- **패턴/원칙:** "한 페이지에 여러 분기" vs "페이지 단위 분기"는 다른 메커니즘. 워크로그는 전자(placeholder), staticrypt는 후자(페이지 통째). manifest를 중간 인터페이스로 두면 두 메커니즘이 깔끔히 분리됨. 향후 페이지 단위 보호가 필요한 다른 콘텐츠 타입도 같은 manifest로 통합 가능.
- **새로 통한 것:** `staticrypt`는 npm dev-dep로 충분(빌드 타임에만 호출, 런타임 의존 0). 8개 vulnerability 경고는 dev-only라 production 노출 없음 — npm audit fix는 보류해도 안전.
- **막힘 회복:** fixture를 정적 commit 대신 sync-content가 매번 생성하도록 박음. 재현성·결정성 우선, content 비우기 흐름과 충돌 회피.
