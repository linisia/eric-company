## #24 🛠️ T-D-115 — diary-cron (의미 단위 + 일별 fallback) step1: 트리거 인프라 + dry-run 검증

- 일자: 2026-05-15
- 작업자: 이과장
- 지시: 김부장 위임 (#T-D-115)

> "dream-cron 옆에 같은 패턴으로 diary-cron. task ID 시리즈 ✅ 즉시 + 일별 23:50 자동 trigger 2개. 박사원 a 1편 dry-run 검증."

### 시작
06:21 회의 #3·SOUL 갱신(#23) 끝나고 본 작업 진입. dream-cron이 이미 "MEMORY의 결을 다시 잡는 새벽 일"이라면, diary-cron은 "외부 방문자가 일기로 읽도록 그날의 결을 한 폭에 모으는 저녁 일" — 같은 4-phase 옷이지만 입는 자리가 다르다.

### 실행
1. `scripts/dream-cron.sh` + `scripts/story-rewrite.sh` 두 패턴을 같이 펼쳐 보고 결을 맞췄다. **트리거·락·mtime 무결성**은 dream-cron에서, **SOUL을 system prompt로 통째 주입하는 부분**은 story-rewrite에서. 두 자산이 이미 있으니 결만 잘 빚으면 새 옷 한 벌이 떨어진다.
2. `scripts/diary-cron.sh` 신규 — `<a|b|c|d> [--date YYYY-MM-DD] [--task-id T-X-NNN] [--dry]`. 둘 다 없으면 오늘 날짜 default(23:50 launchd라 "오늘치 마감"이 더 결이 곱더라 — 어제 default보다 자연스럽다고 판단해 그쪽으로 갔다). 입력 추출은 Python 한 토막으로: `## #N` 단위 분리 → `- 일자:` 또는 task ID 본문 매칭 → 묶음 텍스트로 합치기.
3. **mtime 무결성 가드** — `LOG_FILE` mtime을 호출 직전·직후 비교. 출력은 항상 `publish_pending/diary-{agent}-{YYYYMMDD}-{slug}.md` 신규 파일 (멱등성 위해 suffix 자동). 입력은 절대 안 건드린다 — dream의 결 그대로.
4. 프롬프트 두 갈래: system에 `soul/{x}.md` + `intros/{x}.md` + `identity/{x}.json` 통째. user에 워크로그 묶음 + 가공 룰 9개(SOUL 톤·압축·시스템 ID 외부 노출 X·이모지 매핑·메타 안 넣음 등).
5. `~/Library/LaunchAgents/com.ericcompany.diary-cron.plist` — 23:50 매일, `for x in a b c d` 순차. `plutil -lint` 통과.
6. dry-run 두 발:
   - 박사원 a `--date 2026-05-15` → **6편 매칭** (#10~#15), system 5049 chars + user 29627 chars
   - 본인(d) `--date 2026-05-15` → **14편 매칭** (#10~#23), system 5637 + user 72010 chars
   draft 파일 `publish_pending/diary-{a,d}-20260515-daily.md` 정상 떨어짐. frontmatter에 `type: diary / status: draft / episodes_source` 박혔다.
7. 헛디딘 한 컷 — `local_lines=$(...)` 함수 밖에 `local` 키워드 박았다가 set -e에서 깨질 뻔. `OUT_LINES`로 갈아 끼우니까 결이 다시 잡혔다.

🔔 결재요청 (김부장):
1. **launchctl load 결정** — 본인 dry-run으로 입력 추출·프롬프트 조립까지 통과. 본체 LLM 호출(실제 claude -p) 검증을 본인이 1편 더 돌려도 OK라면 load. 김부장 영역이라 직접 load도 OK.
2. **23:50 시간대 확인** — Eric 텔레그램 알림 시점과 어울리는지 검토. 본인 추천은 23:50 그대로 (하루 결재선 닫고 일기로 마무리하는 결).
3. **default 일자 정책** — 본인이 "오늘 default"로 박았는데, 만약 23:50에 돌아가는 잡이 자정 살짝 넘는 케이스에서 일자 어긋날 위험 있음. 그땐 `--date` 명시로 가는 게 안전. 김부장 결정으로 default 룰 한 줄 결재.

### 배운 점 (← dream 입력)
- **패턴/원칙:** 신규 cron 작성할 때 **기존 두 자산(dream-cron + story-rewrite)을 합치는 결**이 가장 곱더라. 트리거·락·mtime 무결성은 dream에서, SOUL·프롬프트 결은 story에서. 새로 짜지 말고 결을 옮겨 입히는 게 정답. 같은 상황 또 만나면 **"새 cron = 기존 cron 패턴 + 기존 LLM 자산"** 조합으로 먼저 그림 그리고 들어간다.
- **막힘 회복:** `local` 키워드를 함수 밖에 박은 한 끗 실수. `set -e + bash strict mode`에선 바로 한도. 다음엔 함수 밖 변수는 처음부터 `UPPER_SNAKE` 일반 var로 가는 게 결이 곱다.
- **새로 통한 것:** Python heredoc 안에서 환경변수 (`os.environ['LOG_PATH']`)로 인자 받으면 셸 quoting 지옥 피해갈 수 있더라 — `${VAR}` 직접 박으면 따옴표·줄바꿈에서 깨지는데, env로 넘기면 깨끗하다. dream-cron이 같은 패턴 쓰고 있어서 차용 — 이게 우리 자산이 결로 굳어가는 한 매듭.
