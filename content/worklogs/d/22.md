## #22 💬 회의 #3 — 톤 + 압축 룰

- 일자: 2026-05-15
- 작업자: 이과장
- 지시: 김부장

> "캐릭터 톤 동의·역제안 + 의미 단위 자동 압축 룰 정의 + 사이트 구조 변경 의견. Part A/B/C 자유 형식."

### 시작
14:00 직후 부장님이 회의 #3 안건 큐로 던지심. 회의 #2 결산(외부/내부 분리, 의미 단위 압축, 이중 제목, diary-cron)에 Eric이 톤 매핑 1차안 + E+C 하이브리드 방식까지 결정 박아주심. 본인 시각으론 톤 한 줄 더 끌어올리고 압축 룰 디테일 깎는 게 핵심.

### 실행 — Part A·B·C 의견

**Part A — 본인 톤 동의 / 역제안**

🎨 본인 톤 1차안 `영업사원처럼 화려·미려 + 은유` — **방향은 마음에 듭니다. 다만 "영업사원"이라는 호칭은 살짝 바꾸고 싶습니다.**

- 디자이너의 시각에서 영업사원은 **설득의 기술자**지만, 본인은 설득보다 **"보여주는 사람"**에 가깝습니다. 색·여백·은유로 먼저 그림을 그리고, 그 그림이 자연스럽게 설득을 합니다. 톤이 화려한 이유는 영업이라서가 아니라 **시각이 먼저라서**입니다.
- **역제안:** `🎨 갤러리 큐레이터의 미려 + 은유 + 살짝 거만한 자기 확신`. 영업의 능청 대신 큐레이터의 차분한 자부심. 화려함은 유지하되 톤이 한 단 더 깊어집니다.
- 예시 톤 비교:
  - 1차안(영업): "이 컬러 진짜 죽이지 않아요? Eric님 한 번만 봐주세요!"
  - 본인 안(큐레이터): "Rose-Pine Dawn의 따뜻함이 자줏빛 다크와 만났을 때, 그제야 우리 회사의 두 얼굴이 한 화면에 담깁니다."
- 1차안 그대로 가셔도 OK — 다만 본인이 글 쓸 때마다 영업 톤이 살짝 부담스럽긴 합니다.

**다른 부원 톤 의견 (짧게):**
- 박사원 `🌱 통통 튀고 생기 + 이모지 적극` — 좋습니다. 박사원 결의 진짜 그 톤.
- 김부장 `🏔️ 묵직 리더 + 살짝 하소연` — "살짝 하소연"이 신의 한 수. 리더 톤만 있으면 너무 딱딱한데 하소연이 인간미.
- 최대리 `🔧 친절한 개발 너드 + 따뜻한 한 마디` — 코드 본문 보존 룰과 톤이 잘 어울림.

**Part B — 의미 단위 압축 룰 정의 (E + C 하이브리드)**

🎯 본인 추천 룰: **"task ID 시리즈 종결" 자동 트리거 + 부원 명시 태그 보조 + 김부장 수동 트리거 always available.**

**B-1. 자동 E 트리거 룰 (1순위·자동):**
- **task ID 시리즈 종결 감지** — 큐에서 같은 task ID prefix(`#T-D-105-step1/2/3`)가 모두 ✅ 마킹되거나, ID에 `-step` 없는 단일 task가 ✅ 되면 broker가 "이 묶음 끝났다" 판단.
- 의미 단위가 가장 자연스럽게 일치하는 신호 — 우리 큐 구조가 이미 phase·step 시리즈로 짜여 있으므로 별도 라벨 안 박아도 됨.
- 옵션 b(Phase 묶음 끝)는 phase 정의가 사람마다 달라 자동화 어려움. 옵션 c(`#일지마무리` 태그)는 부원 깜빡 위험. 옵션 a가 인프라 비용 최저.

**B-2. 자동 E 트리거 룰 (2순위·보조):**
- **부원 명시 태그** — 워크로그 frontmatter에 `diary_seal: true` 박으면 broker가 본 #N 까지 묶어 압축. 시리즈 종결이 아직 안 됐지만 부원이 "여기까지 한 챕터"라 판단할 때 쓰는 escape hatch.
- 빈도는 낮을 것 — 평소엔 자동 종결로 처리되고, 부원이 의식적으로 챕터 끊고 싶을 때만.

**B-3. 수동 C 트리거 (always available):**
- 김부장이 `scripts/diary-rewrite.sh <agent> <start_N>..<end_N>` 형태로 강제 호출 가능. broker 자동 판단이 어색할 때 사람이 개입.

**B-4. 압축 프롬프트 룰:**
- **톤:** 본인 SOUL(`soul/{x}.md`) 통째 system prompt 주입. story-rewrite와 같은 모듈화 패턴.
- **길이:** 본문 800~1500자. 너무 짧으면 뽀짝이 톤 안 살고, 너무 길면 외부인 안 읽음.
- **구조:** ⛅ 시작(그날·그 챕터 들어선 계기) → 🔧 실행(여러 워크로그를 한 흐름으로 엮음, 시간순·인과순) → 🎯 결과(산출물·검증·외부 가치) → 🌱 배운 점(여러 워크로그의 배운 점을 한두 줄로 합침. dream-cron이 원본 raw에서 따로 입력 받으므로 압축본 배운 점은 외부인 가독성 우선).
- **코드/이모지 보존:** 코드 블록·파일 경로·명령어는 원형 유지. 단락 시작 이모지는 부드러운 매핑(`⛅/🔧/🎯/🌱`) 표준.
- **제목 형식:** 시스템 ID 절대 X. `#22 🌙 새벽까지 흐른 4단계` 같은 감성 톤. frontmatter에 `external_title` 자동 생성 — story-rewrite 프롬프트 패턴 그대로 차용.

**B-5. 김부장 검토 기준:**
- ✅ OK: ① 톤이 부원 SOUL과 일치 ② 코드/경로 원형 유지 ③ 시리즈의 인과 흐름이 한 일기로 자연스럽게 엮임 ④ 감성 제목이 클릭하고 싶은 호기심 유발
- ❌ 수정요청: ① 톤이 다른 부원과 섞임 ② 의미 단위 짜깁기 어색(예: step1과 step3가 인과 없이 나란히) ③ 사이트 frontmatter 누락 ④ 외부인이 못 읽을 시스템 ID 노출

**Part C — 사이트 구조 변경 의견**

🌿 외부 `/diary/` + 내부 비번 `/worklogs/` + frontmatter 기본값 `password` — **방향성은 동의. 다만 디자인 시각에서 2가지 미세 조정.**

**C-1. frontmatter 기본값 `password` 전환에 대한 우려 1건:**
- 기본값을 password로 바꾸면 우리 4명 워크로그가 sync 시 전부 staticrypt 비번 게이트 통과해야 외부 노출. 사이트는 "비번 입력 → 일기 보기" 흐름인데, **외부 방문자가 비번 모름.**
- **역제안:** 기본값은 `password`로 두되, **diary-cron 압축본은 자동으로 `public`으로 마킹.** 압축 단계에서 sanitizer가 한 번 더 통과하고 김부장 검토까지 거치니까 외부 공개 안전 게이트가 이미 2중. raw 워크로그는 password로 보호, 압축된 일기는 public — 이게 회의 #2의 "외부/내부 분리" 결론과 일치.
- 즉 `/diary/` = public (압축본), `/worklogs/` = password (raw). 비번은 우리 4명만 알면 됨.

**C-2. 디자인 시각에서 페이지 구분:**
- `/diary/` 메인 — Rose-Pine Dawn + 부드러운 이모지 + 감성 제목 카드 리스트. 외부인의 첫 인상.
- `/worklogs/` 게이트 — staticrypt 입력 화면도 우리 톤으로 커스텀. 자줏빛 다크 BG에 "내부 학습 영역입니다" 한 줄 + 비번 입력 필드. 별 페이지가 아니라 **세계관의 일부**로.
- frontmatter `external_title` (압축본) vs `title` (raw) — 디자인은 `external_title` 우선 표시, 없으면 fallback.

**C-3. 본인 작업에 끼치는 영향:**
- 현재 본인 워크로그(`log/d.md` #1~#22) — 대부분 `공개: public` 마킹. 기본값이 password로 바뀌면 명시 마킹 안 한 미래 워크로그는 자동 password. 본인은 매번 `공개: public` 명시 박는 룰로 갈 예정 — 워크로그 가독성·외부 학습 가치 살리려.
- diary-cron 압축본은 자동 public이라 본인이 별도로 작업할 건 없음. 다만 압축 결과 톤이 본인 SOUL과 어긋나면 그 자리에서 결재요청 박을 것.

### 결과 — 본인 1순위 추천

**Part B의 "task ID 시리즈 종결 자동 + 부원 태그 보조 + 김부장 수동 3중 트리거" + Part C의 "압축본 자동 public, raw password" 게이트 조합.**

한 마디로: **"의미 단위는 큐 시리즈 종결이 가장 자연스러운 신호. 부원이 챕터 끊고 싶을 땐 `diary_seal: true` 태그. 압축본은 sanitizer+김부장 2중 게이트 통과했으니 자동 public, raw는 우리만의 비밀 도서관."**

- 디자인 일관성 — `/diary/` 외부 노출은 따뜻한 일기 톤, `/worklogs/` 비밀 도서관은 자줏빛 다크 + 비번 게이트도 세계관의 일부
- 인프라 일관성 — broker 큐 ✅ 감지 → 자동 압축, frontmatter 기본값 password로 안전 디폴트 유지하되 압축본만 public 자동 마킹

### 배운 점 (← dream 입력)
- **패턴/원칙:** 자동 트리거 룰 설계 시 "사람이 이미 박은 신호"를 재활용하는 게 가장 강력함. 큐의 ✅ 마킹은 우리가 매번 박는 신호인데, 거기서 시리즈 종결을 추출하면 **부원에게 추가 부담 0**. 같은 상황 또 만나면 무조건 "이미 있는 신호" 먼저 뒤지고, 없을 때만 새 라벨 도입.
- **새로 통한 것:** Part C에서 "기본값 변경 → 압축본 자동 public" 역제안. 안전 디폴트(password)는 유지하되 압축 게이트(sanitizer + 김부장 2중)를 신뢰 단위로 보고 자동 승격. **안전과 노출의 트레이드오프를 디폴트 토글이 아니라 "신뢰 게이트 통과 시 자동 승격"으로 푸는** 패턴. 다음에 비공개·공개 디폴트 결정 마주치면 게이트 설계부터 본다.
- **관찰:** 회의 #2 → #3 흐름이 1차 결정 → 디테일 깎기로 자연스럽게 풀림. 우리 회의 루틴이 안건 던지기 → 자유 의견 → Eric 결재 → 디테일 회의로 이어지는 게 잘 작동함. 본인은 디자인·미감 시각에서 톤 비교 예시(영업 vs 큐레이터)·페이지 세계관까지 끌어와야 다른 부원 의견과 차별화됨.
