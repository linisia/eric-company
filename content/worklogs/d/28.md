## #28 💬 회의 #4 — 화면 분석·통찰 누적 방식 의견

- 일자: 2026-05-18
- 작업자: 이과장
- 지시: 김부장 위임 (#T-D-117)

> "Eric 4단 최종 목표(자연어→Figma·Notion 자동 / 화면 ID = Firebase ID / 화면별 중요도·KPI·필요 데이터 / 누적 데이터로 통찰) 중 분석·통찰 측면 안건 2/3. 미감 강점으로 풀어봐."

### 시작
부장님, 본인은 이 회의 안건이 "결을 어디서 잡고 들어가야 데이터가 통찰로 풀려 떨어지는가"라는 한 질문으로 묶입니다. 화면 카드라는 옷감을 결대로 짜 들어가는 결을 빚는 동안, **`priority`·`firebase_event`·`sitemap 의도` 세 결이 한 결로 합쳐지는 자리에서 통찰이 비로소 일어선다**고 보입니다. 본인 톤(영업사원처럼 화려·미려 + 은유)으로 4개 안건 결대로 펼칩니다.

### 실행

#### Q1. 화면 단위 중요도 — 어떻게 정의·누적할 결인가

본인 추천: **3축 누적 점수 + INDEX `priority` 컬럼 단일 SSoT**.

세 결을 한 컬럼에 빚어 떨어트리는 결재선:

| 축 | 결의 모양 | 가중치(1차안) | 신호 출처 |
|----|----------|--------------|----------|
| **(1) Sitemap 의도** | 1 depth·중복 매핑·연결 진입 다발 | 40% | `sitemap.md` 정성 평가 (Eric 구술 기반) |
| **(2) Firebase 통계** | 화면 진입 빈도·체류시간·이탈률 | 40% | Firebase 이벤트 (실측) |
| **(3) Eric 자연어 지시 빈도** | 같은 화면·기능 언급 누적 카운트 | 20% | broker 또는 watcher가 자연어 로그에서 화면 ID grep |

— **결의 결론**: `priority: core | important | background | duplicate | meta` 5단 enum. core/important는 (1)+(2) 둘 다 상위, background는 (2) 하위, duplicate는 sitemap이 같은 의도로 매핑된 별칭, meta는 HM_00 같은 소개 row.

본인 시각으로 한 끗: **3축 점수를 raw로 박지 말고 enum으로 떨어뜨려야 결이 곱습니다.** 숫자(0.73)는 외부 방문자한테 결이 차고 KPI 변동에 따라 매주 흔들립니다. enum은 한 번 박히면 *판단*으로 굳어 사이클이 빨리 돕니다. 숫자는 INDEX 옆 별도 `priority_score` 컬럼(선택)에 박아 두면 결재할 때만 봅니다.

자기 판단·역제안: **`promotion_history` 같은 변동 이력 row가 INDEX 아래에 한 줄씩 누적**되면 더 곱습니다 — `2026-06-01 HM_02: background → important (Firebase 진입 3배)` 같은 결. 통찰 4단에서 "기능이 떴다·졌다"의 결을 시계열로 잡아냅니다.

#### Q2. sitemap.md 양식 — LLM 학습에 충분한가

본인 평가: **현행 양식 결은 곱지만 LLM 입력으로는 한 결 부족**.

✅ **결이 곱게 잡힌 자리:**
- 1 depth 표 + 카테고리 분류(메인 5/그 외) — LLM이 prefix → 카테고리 한 결로 잡음
- Eric 구술 그대로 인용("*홈 화면은 그냥 이 화면이 대부분임*") — 의도 결이 살아 있음
- 중복·겹침 매핑 표 — duplicate enum의 입력으로 바로 떨어짐
- 변경 이력 append-only — 결의 시간축 보존

⚠️ **결이 끊긴 자리:**
1. **machine-readable frontmatter 부재** — LLM 학습엔 가독성 좋지만 broker가 화면 ID 기준으로 grep할 때 결이 끊깁니다. `### GL_01 — 메인메뉴` 같은 헤더가 결구조라 정규식 한 줄로 잡기는 가능하지만, **YAML block table 한 발 추가**가 곱습니다.
2. **`intent_keywords` 결이 없음** — Eric 구술의 "어디서나 호출되는 글로벌 진입점" 같은 표현이 자연어 결로 박혀 있는데 LLM 임베딩하려면 키워드 결이 같이 박혀야 합니다. (예: `intent_keywords: [global, sidebar, navigation]`)
3. **연결 그래프 구조 부재** — `연결 진입` 줄에 텍스트로 박혀 있는데 그래프 시각화·중심성 분석은 결이 안 잡힙니다. 산출물 결로 **`sitemap.graph.json`** (node + edge) 별도 빌드 제안.
4. **2 depth 이하 자동 탐색 결과 통합 룰** — 글로벌 룰 #5에 "부원 자동 탐색" 박혔는데, 부원 결과를 어디에 어떻게 append할지 결이 안 잡혔습니다. **`## {Prefix} 자동 탐색 결과`** 서브섹션 룰 박는 게 곱습니다.

본인 추천 1순위: **`### {ID} — {이름}` 헤더 아래 4줄짜리 frontmatter table 룰 추가**. `intent_keywords` + `priority` + `firebase_event_candidate` 3개. 자연어 본문은 그대로 보존 — 결의 시각적 미려함도 살고, machine-readable도 살고.

#### Q3. Firebase 이벤트 매핑 — 어떤 단위에 박는 결이 곱은가

본인 추천: **카드 단위 박힘 + INDEX 자동 미러링 + `firebase_events.yaml` SSoT 보조**.

세 결의 트레이드오프:

| 단위 | 곱은 결 | 차한 결 |
|------|---------|--------|
| **카드 단위** (frontmatter `firebase_event: vd_list_view`) | 화면 컨텍스트 옆에 박힘 — 결재선 곱음. 카드 수정 시 결 같이 갱신 | 200+ 카드 흩어져 일관성 깨질 위험 |
| **INDEX 단위만** | 한눈에 매트릭스 보임 — 통계 인프라 박기 쉬움 | 카드 안에서 이벤트 못 보고 결이 끊김 |
| **별도 SSoT** (`firebase_events.yaml`) | enum·네임 컨벤션 한 결로 잡힘 — 검증·중복 막음 | 카드와 결이 분리되어 동기화 부담 |

— **하이브리드가 결이 가장 곱습니다.**
1. **SSoT는 `products/MOL4/wiki/firebase_events.yaml`** — enum·네임 컨벤션 박음 (`{prefix}_{screen}_{action}_v1` 같은 결).
2. **카드 frontmatter는 SSoT의 키만 인용** — `firebase_event: vd_list_view`.
3. **INDEX는 자동 미러링** — 카드 frontmatter 모아 INDEX 컬럼에 떨굼 (다음 사이클에 미러 스크립트 작성 가능).

본인 자기 판단: **네임 컨벤션은 `snake_case_v1` 결로 시작**. 버전 suffix는 결이 흔들릴 때(`v2`) 결재선 곱게 깔립니다. Eric 결재 받아 박으면 200+ 카드에 일괄 적용 시 흔들림 없습니다.

#### Q4. 분석·통찰 4단 (최종 목표) — 어떤 데이터가 모이면 통찰 가능한가

본인 시각: **세 결이 한 결로 합쳐지는 자리에서 통찰이 일어선다.**

```
(A) 정성 결 — sitemap.md 의도·중복
(B) 정량 결 — Firebase 진입·체류·이탈
(C) 시간 결 — Eric 구술 변경 이력 + promotion_history
                       ↓
                  통찰 결 자리
```

**통찰이 일어서는 3가지 결 (1차 가설):**

1. **불일치 결** — *"Eric이 important로 박은 화면이 Firebase는 background로 떨어진다"*. (A) ↔ (B) 격차 자리. 결: 화면이 의도대로 안 도착했다 → UX 결재 진단.
2. **떴다·졌다 결** — *"6주간 background였던 HM_02가 important로 promotion된 결"*. (C) 시간축에서 잡힘. 결: 기능이 늦게 결을 잡았다 → 마케팅·릴리즈 노트 결재 진단.
3. **숨은 허브 결** — *"sitemap 연결 그래프 중심성은 낮은데 Firebase 진입은 상위"*. (A) ↔ (B) 또 다른 격차 자리. 결: 외부 진입(딥링크·검색·푸시)이 결을 만들고 있다 → 마케팅·SEO 결재 진단.

**모여야 할 데이터 (최소 SSoT):**
- `sitemap.graph.json` — 노드(화면 ID)·엣지(연결 진입)·중심성 점수
- `firebase_events.yaml` — 이벤트 정의·네임 컨벤션
- `firebase_stats_weekly.json` — 주간 화면별 진입·체류·이탈 (이건 외부 데이터 — Firebase Analytics에서 자동 추출 패턴 별도 결재 필요)
- `priority_history.yaml` — 화면별 priority enum 변동 시간축
- `eric_voice_index.yaml` — 자연어 지시에서 화면 ID grep된 빈도 (broker가 매주 자동 누적)

— **본인 자기 판단**: 6주~8주 누적 데이터가 모이면 통찰 결 한두 개는 분명히 일어섭니다. *지금 시점*에서 결을 곱게 잡아야 하는 자리는 **(C) 시간 결의 frontmatter 결재선** — sitemap 변경 이력은 이미 잘 박혀 있고, priority_history는 본 회의 결과 박히면 시작됩니다. 이게 차곡차곡 쌓이면 8주 뒤에 첫 통찰 결재안이 곱게 떨어집니다.

### 배운 점 (← dream 입력)
- **패턴/원칙:** 분석·통찰 설계에서 결이 가장 곱지 않은 자리는 **"어떤 데이터를 모을지"가 아니라 "어디에 어떻게 박을지"**다. SSoT 결재선(카드 단위·INDEX 단위·별도 yaml)이 흔들리면 200+ 행 데이터가 결을 못 잡는다. 같은 상황 또 만나면 데이터 항목 결정 *전*에 SSoT 위치·네이밍·동기화 결을 먼저 빚는다.
- **새로 통한 것:** 정성(sitemap) ↔ 정량(Firebase) ↔ 시간(history) **세 결의 격차 자리에서 통찰이 일어선다**는 결의 모양. 격차가 곧 가설 — 일치하는 자리는 통찰 결재안이 나오지 않는다. 다음 분석 설계 시 "격차를 어디서 잡을 결인가"를 먼저 결정해야 결이 곱다.
- **막힘 회복:** Q3에서 카드 단위 vs INDEX 단위 vs 별도 SSoT 셋 다 결이 일리 있어 한순간 결이 흔들렸지만, **하이브리드(셋 다 한 결로 묶고 SSoT가 enum 잡음)**로 결을 합쳐 떨어뜨려 결이 풀렸다. 같은 결로 흔들리는 자리에선 셋을 분리하지 말고 한 결로 묶을 길을 먼저 본다.
