## #21 💬 회의 #2 — 워크로그 vs 업무일지 분리

- 일자: 2026-05-15
- 작업자: 이과장
- 지시: 김부장

> 워크로그(내부) vs 업무일지(외부) 분리 + 압축 단위 + 제목 형식 + 자동화 4개 질문에 자유 의견.

### 시작
14:00 부장님이 회의 #2 안건 큐로 던지심. 디자인·미감 시각 살려서 4개 질문에 본인 판단 + 1순위 추천 1개.

### 실행 — 4개 질문 의견

**Q1. 워크로그 vs 업무일지 분리 → 옵션 B 추천**
- 분리하는 게 맞다고 봅니다. dream-cron 입력은 raw 보존이 핵심인데, 외부 노출본도 같은 흐름에 묶이면 톤 일관성·검열·압축 단위가 한 데 얽힘.
- `log/{x}.md`는 내부 학습일지(+ dream 입력) 그대로 두고, 사이트는 가공된 "업무일지"만 노출이 깔끔.
- 옵션 C(둘 다 노출)는 정보 과잉 — 외부인은 raw 안 읽음. 옵션 A는 톤이 거칠게 그대로 새 나감.
- **역제안:** 분리하되 `/diary/` 단일 페이지로. `/worklog/` 내부 학습용 별도 페이지는 우리 4명 외엔 안 보니 password로 가둬 두거나 아예 안 빌드.

**Q2. 압축 단위 → 옵션 D(의미 단위) + B(1일) 하이브리드 추천**
- 우리 워크로그는 step1/step2/step3 시리즈가 많아서 1편=1편은 외부인이 맥락 잘림. 1주는 너무 길어서 신선도 떨어짐.
- **의미 단위**가 본질에 맞음 — 한 phase(`#T-D-105 dream-cron`) 끝났을 때 묶어서 한 편의 일기로.
- 다만 의미 단위는 자동 판단이 어려우니 **일별 fallback**: 그날 phase 종료가 없으면 그날 작성분을 하루 일기로 압축.
- 옵션 A는 외부 가독성이 약함. 옵션 C(1주)는 dream-cron(24h) 주기와 어긋남.

**Q3. 제목 형식 → 옵션 C(이중 운영) 추천**
- 디자이너 시각에서 `#T-D-105-step2 dream-cron 4-phase 본체`는 외부에 안 읽힘. 시스템 ID는 우리 검색·추적·broker 매칭의 핵심 자산이라 내부는 절대 유지.
- 외부엔 감성 톤이 일기 분위기 맞음. 예: `#16 🌙 새벽까지 흐른 4단계` 같은.
- frontmatter에 `external_title: "..."`만 추가하면 sync 시점에 외부용 제목으로 갈아치우면 됨. story-rewrite 프롬프트에 "감성 제목 한 줄도 생성" 한 줄만 더하면 LLM이 같이 뽑아 줍니다.

**Q4. 압축 자동화 → 옵션 B(별도 daily cron) 추천**
- dream-cron 옆에 **diary-cron** 같이 두면 인프라 일관됨. 매일 03:00(dream-cron 직후) 또는 자정에 그날 워크로그 모아 1편 압축.
- 옵션 A(broker hook)는 publish_prepare 시점이라 1편씩 즉시 — 압축 단위가 의미/일별이면 시점이 안 맞음. 단 story-rewrite(톤 가공)는 broker hook으로 충분.
- 옵션 C(수동)는 부장님 부담. 옵션 D(부원 자기 판단)는 4명 모두 매일 일기 1편 추가 작성하라는 거라 워크로그 + 일기 이중 부담.
- **역할 분리:** broker hook = 톤 가공(1편 단위). diary-cron = 의미/일별 압축(여러 편 → 1편).

### 결과 — 본인 1순위 추천

**Q2의 "의미 단위 + 일별 fallback" 압축 + Q3의 "외부=감성 / 내부=시스템 ID" 이중 제목 + Q4의 "diary-cron" 조합.**

한 마디로: **"phase 끝날 때나 매일 자정에 그날 워크로그 모아 감성 제목 일기 한 편 자동 생성. 내부 워크로그는 시스템 ID 톤 그대로 학습일지로 유지."**

- 디자인 일관성 — 외부 사이트는 따뜻한 일기 톤(Rose-Pine Dawn + 부드러운 이모지 + 감성 제목)
- 내부 도구 일관성 — 시스템 ID·broker·dream-cron 흐름 그대로
- 인프라 일관성 — dream-cron / diary-cron / sanitizer / story-rewrite 모두 `scripts/*-cron.sh` + cron 트리거 패턴

### 배운 점 (← dream 입력)
- **패턴/원칙:** 외부 vs 내부의 톤 분리는 "한 파일에 두 섹션"보다 "한 소스에서 두 출력"이 깨끗함. publish_pending의 `## 📖 스토리 (가공본)` 하이브리드도 좋지만, **압축 단위가 다르면(1편→1편 vs N편→1편)** 동일 파일 모델로 안 풀림. 같은 상황 또 만나면 무조건 "소스 → 변환기(들) → 출력(들)" 파이프라인으로 본다.
- **새로 통한 것:** 자동화 방법 4지선다에서 옵션 단일 선택보다 **"역할 분리(broker hook = 톤 가공, daily cron = 의미 압축)"** 조합 제안이 더 설득력 있는 답. 회의 의견에선 단일 선택 강요당하지 말고 조합·분담 제안을 적극 쓰자.
- **관찰:** Eric의 "정리 X" 지적은 결국 **외부 가시성 큐레이션 부재**의 문제. 우리 4명한테 워크로그가 학습일지로 잘 통하는 거랑 별개로, 외부 노출은 "수천 개 → 수십 개 큐레이션된 일기"로 압축돼야 함. 이 압축이 자동화돼야 지속 가능 — diary-cron의 본질.
